# RR Capital database rebuild and recovery

The checked-in migration chain starts with `20260930000000_initial_schema.sql`, a schema-only snapshot of the pre-hardening RR Capital public schema. `supabase/New-SanitizedBaseline.ps1` replaces the legacy Telegram trigger body with a no-op before the baseline is written; the original private dump must never be committed. `20260930000001_auth_profile_trigger.sql` restores the profile-creation trigger on `auth.users`, which a public-only dump cannot contain.

For a **new** Supabase project, provision the normal Supabase auth and extension schemas, then apply every file in `supabase/migrations` in filename order. Do not load production user data into a test project. Keep project secrets, Telegram bot token, and webhook secret out of migrations and source control. Configure the Edge Function secrets separately and rotate the old embedded bot token before using Telegram.

For the **existing** RR Capital and Financial OS v2 projects, first compare live schema and migration history against this baseline. The baseline recreates tables/functions and must **not** be executed over an existing schema. Record the baseline and any already-applied hardening migrations as applied only after verifying their objects and definitions. For RR Capital, this reconciliation was completed on 2026-10-01: verified existing versions were recorded in the migration ledger, then the six remaining hardening migrations were applied. A fresh `db push --dry-run` reported no pending migrations. A private schema-only and pre-hardening data-only snapshot were created. A full restore rehearsal to an isolated Supabase project remains outstanding. Financial OS v2's migration history and deployment were not changed in this step.

The local clean-rebuild check used a separate PostgreSQL database with `supabase/tests/local_supabase_stub.bootstrap.sql` to stand in for Supabase-managed auth and extensions. The sanitized baseline and all later migrations applied in order. All ten `*.test.sql` files passed with `ON_ERROR_STOP=1`; they wrap fixtures in `BEGIN`/`ROLLBACK`. The final check found zero `auth.users`, zero transactions and settlements, and exactly one profile-creation trigger. This proves local migration ordering and tested SQL behavior; it does not prove live Supabase platform configuration, Edge Function secrets, backups, Storage, or Vercel deployment.

The local stub is **only** for an isolated PostgreSQL test database. Never run it against a Supabase project. The original schema dump is a historical backup artifact and contains an old credential; it remains outside Git under `C:\Users\ridhw\rr-capital-remediation` and must be handled under the user's backup/retention plan after rotation.
