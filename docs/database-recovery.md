# RR Capital database rebuild and recovery

The checked-in migration chain starts with `20260930000000_initial_schema.sql`, a schema-only snapshot of the pre-hardening RR Capital public schema. `supabase/New-SanitizedBaseline.ps1` replaces the legacy Telegram trigger body with a no-op before the baseline is written; the original private dump must never be committed. `20260930000001_auth_profile_trigger.sql` restores the profile-creation trigger on `auth.users`, which a public-only dump cannot contain.

For a **new** Supabase project, provision the normal Supabase auth and extension schemas, then apply every file in `supabase/migrations` in filename order. Do not load production user data into a test project. Keep project secrets, Telegram bot token, and webhook secret out of migrations and source control. Configure the Edge Function secrets separately and rotate the old embedded bot token before using Telegram.

For the **existing** RR Capital and Financial OS v2 projects, first compare live schema and migration history against this baseline. The baseline recreates tables/functions and must **not** be executed over an existing schema. Record the baseline and any already-applied hardening migrations as applied only after verifying their objects and definitions. For RR Capital, this reconciliation was completed on 2026-10-01. Applied versions include atomic/idempotent ledger and payment operations, balance validation, Telegram linking, receipt rate limits, encrypted per-user Gemini keys, write-boundary hardening, query-performance hardening, and creator notifications for request acceptance/decline. Two later grant-hardening migrations (20261001092558 and 20261001092901) restrict balance/category table privileges, hide private trigger functions from RPC, and explicitly revoke anonymous grants. The latest RR Capital migration `20261002030000_notify_creator_on_request_response.sql` adds minimal Telegram notices to the request creator after an obligation, EMI, or settlement is accepted or declined. The Edge Function was deployed first; the migration was then applied, and CLI migration history now matches with no pending migrations. The webhook URL and secret are present in Vault; their values were not read. Notification delivery depends on the creator having linked Telegram. No account identifier, amount, or other financial details are sent in the response alert. A full restore rehearsal to an isolated Supabase project remains outstanding.

## Managed-platform security follow-ups

The live Auth leaked-password protection flag is still disabled. A one-setting Management API update was attempted and Supabase rejected it with “available on Pro Plans and up”; do not silently change project billing or relax this requirement. Enable it after an authorized plan change, then confirm `password_hibp_enabled=true` and rerun the security advisor. The current project password minimum is six characters; changing it may affect existing sign-ins, so assess the active account before raising it.

All four internal workflow/audit tables now have RLS enabled with no API-role table grants. Access continues through existing scoped `SECURITY DEFINER` functions. The current RR Capital security advisor reports informational `rls_enabled_no_policy` notices for tables with no direct grants, the managed `pg_net` placement warning, and leaked-password protection disabled. A direct catalog query shows the transactions table has only its owner-scoped SELECT policy, while the performance advisor still names old permissive transaction policies absent from that catalog result. Resolve this advisor/catalog discrepancy before relying on advisor output as a complete access-control check.

The production migration advisor identified two missing child-side FK indexes for category deletion and owner cleanup. Both indexes are now applied and the migration history is aligned. The remaining “unused index” notices reflect the freshly cleared, almost empty production data set; retain these FK and workflow indexes until workload evidence supports removing any one of them.

The local recovery directory is outside the repository but contains plaintext webhook-secret and Vercel environment backup files alongside SQL snapshots. The three environment files and five `production-*` recovery snapshots now have protected ACLs granting FullControl only to the current owner, SYSTEM, and Administrators; the previously inherited additional local account has no access to these files. No file contents were changed. A metadata-safe token-format scan found one previously rotated Telegram bot token in the local historical schema dump; it remains outside Git under the protected ACL and should be removed under the user's backup-retention decision. A full local Gitleaks CLI scan was unavailable in this environment; the public repository was not given these local recovery artifacts.

The production `pg_net` extension remains installed in `public`, and its functions are owned by Supabase's `supabase_admin`; the project database role cannot revoke those managed grants. The checked-in API configuration exposes only `public` and `graphql_public`. On 2026-10-01, a read-only PostgREST request using the production public key and an intentionally nonexistent table with `Accept-Profile: net` returned `406 PGRST106 Invalid schema: net`, confirming `net` is not exposed to API clients. The extension-in-public advisor warning remains because the managed extension is installed in `public`; it is not the same as exposing the `net` schema.
