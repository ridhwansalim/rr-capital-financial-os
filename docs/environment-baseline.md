Existing accounts are backfilled with a zero opening position at their earliest linked ledger date to preserve current ledger-derived balances; new accounts accept a dated starting balance, and a database trigger rejects ledger entries before either account endpoint's opening date. A user may correct the baseline before the first ledger row; thereafter the baseline is immutable. The transaction guard takes all changed account endpoint locks in sorted UUID order to reduce opposite-direction transfer deadlocks.

Migration `20261002040700` replaces the net-only liquid balance check with a chronological running-balance invariant. It evaluates all account movements ordered by their event timestamps, checks the candidate entry immediately, and rechecks the final transaction state at commit so voids/replacements cannot leave subsequent history overdrawn. The SQL regression proves an invalid backdated debit is rejected even when later income leaves a positive final balance, a backdated debit funded by every later event is accepted, and voiding prior income that would overdraw later history is rolled back. This migration is local-only and has not been applied to hosted RR Capital.

Chitti and personal bank EMI occurrences are generated from the original start date, anchoring each month to its original day and clamping short months without drifting; the Calendar uses the same rule. An EMI's inclusive `end_date` includes a clamped occurrence only when its due date is on or before that date (Jan 31 through Feb 28 includes February, ending Feb 27 does not). Historical installments are inserted as `UNCONFIRMED`, never inferred from aggregate counters. The Chittis and Calendar screens let the user mark each past occurrence Paid before setup (history-only; no ledger row) or Missed, and payment RPCs can then pay a selected unpaid month atomically with its ledger entry. A past occurrence left unconfirmed is blocked from new payment, preventing accidental duplicate cash movement. The Chittis and personal bank EMI payment RPCs also reject a selected transaction date before the chosen account's opening date; synthetic SQL regressions cover both RPCs, but require local PostgreSQL execution. The later Perry summary migration includes an account's dated opening balance in its personal-balance field. Shared peer EMIs remain on their current two-party settlement flow and are intentionally excluded from this personal installment-history table because payer-side schedule semantics differ.
