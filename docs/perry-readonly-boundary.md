# Perry read-only boundary (local review draft)

Perry is not connected. The role migration, Edge Function, database password, and owner configuration have not been applied to a hosted project. No hosted Supabase or Vercel state has changed.

## Fixed response and data scope

`POST /functions/v1/perry-summary` accepts an empty body and no query parameters. It returns only account names/types/personal balances and aggregate counts, income/expense/transfer totals, and first/last timestamps. It does not return profile fields, row IDs, transaction descriptions/categories, or individual transaction rows. The database aggregation includes only completed transactions whose `owner_id` and `initiator_profile_id` both equal the subject, with no tagged profile/contact and verified owner-owned accounts. It excludes transactions connected to obligations, obligation payments, corrections, Chitti actions, or bank EMI actions. It does not query contacts, shadow contacts, parties, settlements, recurring EMI records, local offline outbox items, or ambiguous/shared records for output.

## Credentials and permission boundary

Perry must sign in as Ridhu through Supabase Auth. Store its rotating refresh token only in Perry's supported operating-system credential store (Windows Credential Manager/DPAPI, macOS Keychain, or Linux Secret Service); keep access tokens in memory and send only short-lived access tokens to this endpoint. The refresh token rotates when used, so Perry must atomically replace the saved token after each successful refresh and erase it on disconnect. Do not put either token in prompts, source/config files, browser storage, logs, or the Obsidian/AI Memory vault. That vault is searchable project memory, not a credential manager. If Perry cannot use a protected credential store, abort the integration rather than fall back to plaintext storage.

The endpoint requires a Supabase user JWT (`verify_jwt = true`) and independently checks it with the RR Capital Auth `/auth/v1/user` endpoint so revoked sessions are rejected before database access. It accepts no query parameters or request body, and derives the subject only from the verified Auth response. The server validates the subject as a UUID before embedding that exact UUID value into its one fixed SQL statement, which sets transaction-local JWT claims and calls `auth.uid()`. The function checks that identity against the private Ridhu owner pin; the RPC accepts no user-ID argument. This sends a simple query through Supavisor transaction mode, which does not support prepared statements. A valid JWT for another user receives a generic access-denied response. Unsupported methods, forged/supplied IDs, and unapproved browser origins are rejected.

The Edge Function uses `PERRY_DATABASE_URL`, a Supabase shared transaction-pooler connection string for a dedicated PostgreSQL login named `perry_reader.<project-ref>`. The URL validator requires the exact RR Capital project reference (`hnebvwfgsotrknxpgpmv`) in the `perry_reader` pooler username, a Supabase pooler host, port 6543, `/postgres`, a strong password, and no query/hash overrides. This makes the function reject the Financial OS v2 project reference. The function uses a pinned Deno Postgres driver, one pool connection, and one fixed SQL statement: `SELECT private.personal_summary()`. Perry never receives the database URL/password, Supabase user JWT, project signing key, service-role credential, or a direct database connection.

The login is created with no password in source. Its password must be generated and set out-of-band, then placed only in the Supabase Edge Function secret `PERRY_DATABASE_URL`. The login is not granted to PostgREST's `authenticator`, has `NOINHERIT` and `NOBYPASSRLS`, has no public-schema USAGE, no table or sequence permissions, and can execute only `private.personal_summary()`. Because PostgreSQL's default `PUBLIC` schema USAGE cannot be revoked for only one login, the migration revokes it from `PUBLIC` and explicitly restores it for Supabase's `anon`, `authenticated`, and `service_role` API roles; Perry has no path to public-schema extension RPCs. The SECURITY DEFINER function recognizes either `session_user = 'perry_reader'` for a direct login or PostgreSQL's protected `role` setting for an explicit role switch, then derives the subject through `auth.uid()` and compares it to the private singleton owner row Perry cannot read or modify. Normal authenticated app clients continue to derive identity from `auth.uid()`. Private-schema default privileges revoke PUBLIC execute on future functions.

This removes the broader signing-key and static integration-token risks in the earlier drafts. A leaked database password alone cannot read another user's data because the database function still requires `auth.uid()` to match the pinned owner. A leaked refresh token remains a sensitive credential: revoke the Supabase session to invalidate it, and keep it only in Perry's OS credential store. Perry has no write or arbitrary query capability.

## Operational gates before connection

1. Apply and test the schema only in an isolated RR Capital clone, never Financial OS v2.
2. Set one owner UUID in `private.perry_owner_config` through an owner-controlled database setup. Confirm there is exactly one row and that account ownership/transaction rules exclude all ambiguous data.
3. Set a unique strong password for `perry_reader`; store it only in the Edge Function secret using the exact transaction-pooler host/username from Supabase Connect. The current Edge role should have a maximum of one connection and transaction pooling is required for short-lived Edge invocations.
4. Deploy only after synthetic positive/negative DB tests pass and verify from the actual deployed function that the pooler logs in as `perry_reader`, the fixed function succeeds, direct table reads/writes fail, the anonymous Data API cannot assume this role, and the returned JSON matches the allowlist.
5. Add endpoint rate limiting/abuse monitoring before connecting Perry. Revoke access by ending the Supabase session/refresh-token family, rotating the database login password, or disabling the function.

No hosted migration, role creation, password setup, deployment, user-data read, Perry token provisioning, or Perry connection has happened. These are still explicit external gates under the previous instruction not to alter hosted state or connect Perry.
